# Task Debug Console Design

Date: 2026-06-18

## Goal

Upgrade the Debug UI task creation panel into a three-engine advanced debug console that matches the current `/api/codeswarm/task/submit` payload and supports `opencode`, `claudecode`, and `script` task creation.

The console should let operators quickly create tasks, inspect the exact payload, validate engine-specific fields before submit, and keep the current real-time task log behavior.

## Current Gaps

The existing Debug UI task form does not fully match backend task creation logic:

- The UI only exposes `opencode` and `claudecode`, while the shared payload schema supports `opencode`, `claudecode`, and `script`.
- The UI does not expose `command` or `scriptCwd`, so it cannot create real script-engine tasks.
- The current advanced `scripts` field can be confused with the `script` execution engine, and the current HTTP submit route does not persist `scripts`, so this UI upgrade should not expose or send it.
- Most fields are shown as one long form, even though each engine has different required and useful fields.
- There is no live payload preview, making it hard to debug the exact request sent to the scheduler.

## Approved Direction

Use a three-column debug workbench:

1. Left column: engine navigation and current configuration summary.
2. Middle column: dynamic task form.
3. Right column: payload preview, validation summary, and templates.

This design was selected over a minimal single-form update and a wizard-style flow because it best supports long-term debugging while keeping all important context visible.

## Layout

### Left Column: Engine Navigation

The left column displays three engine cards:

- OpenCode
- Claude Code
- Script

Selecting an engine updates:

- The engine-specific fields shown in the middle column.
- The payload built in the right column.
- The validation rules used before submit.

The left column also shows a compact summary of shared controls such as selected worker, timeout, workspace state, and whether Tool mode is active.

### Middle Column: Dynamic Form

The middle column contains the main form sections.

#### Base Fields

Shared by all engines:

- `instruction`
- `projectPath`
- `workspacePath`
- `platformTaskId`
- `preferredWorkerNodeId`
- `timeoutSec`

Rules:

- `instruction` remains required for all engines, including `script`, as the task description.
- `projectPath` is sent as a top-level field and merged into `env.INPUT_DIR`.
- `platformTaskId` is merged into `env.PLATFORM_TASK_ID`.
- `timeoutSec` keeps the current UI range: minimum 60, maximum 3600, default 300.

#### Engine Fields

OpenCode fields:

- `model`
- `apiBaseUrl`
- `apiKey`
- `maxTokens`
- `contextWindow`

Claude Code fields:

- `model`
- `apiKey`
- `apiBaseUrl` available as an advanced-compatible field because the backend accepts it.

Script fields:

- `commandJson`
- `scriptCwd`

`commandJson` is edited as a JSON array that maps directly to backend `command: string[]`.

Example:

```json
["python", "run.py", "--target", "/workspace"]
```

The UI does not support shell-like command string parsing. This avoids quoting and whitespace ambiguity and matches the backend's argv-array contract.

#### Tool Dispatch Fields

Tool mode remains compatible with the current backend behavior:

- `toolId`
- `toolPath`
- `toolWorkDir`

Rules:

- Non-empty `toolId` enables Tool mode.
- `toolPath` is sent only when Tool mode is active.
- `toolWorkDir` is merged into `env.TOOL_WORK_DIR`.
- `toolTaskId` is still generated by the backend and is not manually entered in the UI.

#### Advanced Fields

Advanced fields:

- `env` JSON
- `skills`
- `mcps`
- `targetProduct`

Rules:

- `env` must be a JSON object with string values.
- `skills` remains comma-separated and is converted to `string[]`.
- `mcps` becomes JSON input instead of comma-separated input because the backend accepts MCP strings and MCP service objects. The parsed value must be an array. Each array item must be either a non-empty string or an object that matches the minimal MCP service shape accepted by `MCPServiceSchema` in `packages/types/src/index.ts`.
- `scripts` is intentionally removed from this UI upgrade. The current submit route does not read or persist `body.scripts`, and backend API changes are out of scope for this spec.
- `targetProduct` is omitted when empty.

### Right Column: Debug Assistant

The right column is fixed while editing and includes three tools.

#### Payload Preview

The preview displays the exact JSON payload that will be posted to `/api/codeswarm/task/submit`.

Rules:

- Omit empty or `undefined` fields.
- Show the final merged `env` object.
- Show engine-specific fields only when relevant.
- In Script mode, show `command` and `scriptCwd`.

#### Validation Summary

Validation issues are grouped as errors and warnings.

Errors block submit:

- Empty `instruction`.
- Invalid `env` JSON.
- `env` parses to an array or non-object.
- Any `env` value is not a string.
- Invalid `mcps` JSON.
- Parsed `mcps` is not an array.
- Any `mcps` item is neither a non-empty string nor a valid MCP service object. Local MCP objects require `{ "type": "local", "command": string[] }`; remote MCP objects require `{ "type": "remote", "url": string }`, with optional `environment`, `headers`, `enabled`, and `timeout` fields matching `MCPServiceSchema`.
- Script mode has invalid `commandJson`.
- Script command is not a non-empty `string[]`.
- `timeoutSec` is outside the allowed range.

Warnings do not block submit:

- Tool mode is active without `toolPath`.
- OpenCode has no `model`.
- Script has no `scriptCwd`; the worker/backend can fall back to the workspace.

#### Templates

Templates fill common examples without overwriting existing shared fields such as paths, selected worker, and timeout.

Initial templates:

- OpenCode security audit.
- Claude Code code analysis.
- Script command execution.

## Component Design

Keep `TaskDebugPanel` as the container and split form, preview, validation, and templates into focused modules.

Proposed files:

- `packages/debug-ui/src/components/TaskDebugPanel.tsx`
- `packages/debug-ui/src/components/task-debug/EngineSelector.tsx`
- `packages/debug-ui/src/components/task-debug/TaskBaseFields.tsx`
- `packages/debug-ui/src/components/task-debug/EngineFields.tsx`
- `packages/debug-ui/src/components/task-debug/ToolDispatchFields.tsx`
- `packages/debug-ui/src/components/task-debug/AdvancedFields.tsx`
- `packages/debug-ui/src/components/task-debug/PayloadPreview.tsx`
- `packages/debug-ui/src/components/task-debug/ValidationSummary.tsx`
- `packages/debug-ui/src/components/task-debug/TaskTemplates.tsx`
- `packages/debug-ui/src/components/task-debug/types.ts`
- `packages/debug-ui/src/components/task-debug/payload.ts`
- `packages/debug-ui/src/components/task-debug/validation.ts`
- `packages/debug-ui/src/components/task-debug/templates.ts`

Responsibilities:

- `TaskDebugPanel`: owns form state, worker loading, submit, SSE logs, and layout composition.
- `EngineSelector`: renders engine cards and changes the selected engine.
- `TaskBaseFields`: renders shared fields.
- `EngineFields`: dispatches to `OpenCodeFields`, `ClaudeCodeFields`, or `ScriptFields`.
- `ToolDispatchFields`: renders Tool mode inputs and status.
- `AdvancedFields`: renders env, skills, mcps, and target product fields.
- `PayloadPreview`: renders the built payload.
- `ValidationSummary`: renders errors, warnings, and submit-blocking reasons.
- `TaskTemplates`: applies starter templates.

## Data Flow

Use a single form state object in `TaskDebugPanel`. Child components receive the form and a typed update callback.

Extract pure functions:

```ts
buildSubmitPayload(form): SubmitTaskPayload
validateSubmitPayload(form, payload): ValidationIssue[]
applyTaskTemplate(form, template): TaskDebugForm
```

Flow:

1. User edits the form.
2. `buildSubmitPayload(form)` builds the live preview payload.
3. `validateSubmitPayload(form, payload)` returns validation issues.
4. Submit is disabled when any error exists.
5. Submit posts the payload to `/api/codeswarm/task/submit`.
6. On success, existing SSE log streaming behavior continues unchanged.

## Payload Rules

The payload builder should preserve existing behavior where possible:

- Keep `engine` as one of `opencode`, `claudecode`, or `script`.
- Omit empty optional fields.
- Keep `projectPath` top-level and merge it into `env.INPUT_DIR`.
- Merge `platformTaskId` into `env.PLATFORM_TASK_ID`.
- Merge `toolWorkDir` into `env.TOOL_WORK_DIR` when provided.
- Convert comma-separated `skills` to `string[]`.
- Do not send `scripts`; the current submit route ignores it and backend changes are out of scope.
- Parse `mcps` as JSON. The parsed value must be an array. Each item must be either a non-empty string, a local MCP object with `type: "local"` and `command: string[]`, or a remote MCP object with `type: "remote"` and `url: string`. Optional `environment`, `headers`, `enabled`, and `timeout` fields must match `MCPServiceSchema`.
- In Script mode, parse `commandJson` into `command: string[]`.
- Send `scriptCwd` only when non-empty.

## Out of Scope

This change does not include:

- Backend API changes.
- Database schema changes.
- Worker engine behavior changes.
- A new UI component library.
- Shell command string parsing.
- Persistent custom templates.
- Historical task replay.

## Test Strategy

### Implementation-Level Checks

The debug-ui package currently has no test script or test framework in `packages/debug-ui/package.json`, so this spec does not require adding a new test runner.

During implementation, keep payload building, validation, and template application in pure TypeScript functions and verify them through TypeScript compile coverage plus targeted manual/browser checks. If a test framework is added later, these functions are the intended unit-test seam.

Required implementation-level checks:

- OpenCode payload construction.
- Claude Code payload construction.
- Script payload construction with `command` and `scriptCwd`.
- Empty optional field filtering.
- Environment merging for `INPUT_DIR`, `PLATFORM_TASK_ID`, and `TOOL_WORK_DIR`.
- Invalid env JSON.
- Env arrays and non-object values.
- Env values that are not strings.
- Invalid mcps JSON.
- MCP JSON that is not an array.
- MCP array items with invalid string/object shapes.
- Invalid Script command JSON.
- Script command arrays with empty or non-string values.
- Template application without overwriting existing shared fields.

### Type and Build Checks

Run:

```bash
pnpm --filter @codeswarm/debug-ui typecheck
pnpm --filter @codeswarm/debug-ui build
```

If package-level typecheck is unavailable, run:

```bash
pnpm run typecheck
```

### Manual Verification

Start the Debug UI and verify:

- Engine switching updates the form fields.
- OpenCode payload includes only relevant OpenCode fields.
- Claude Code payload includes only relevant Claude Code-compatible fields.
- Script mode accepts JSON array command input and sends `command: string[]`.
- Invalid JSON blocks submit and appears in the validation summary.
- Payload preview matches the submitted request body.
- Task creation still starts SSE logs after success.
- Existing Tool mode behavior is preserved.

## Acceptance Criteria

The implementation is complete when:

- The Debug UI can create `opencode`, `claudecode`, and `script` tasks.
- Script tasks can submit `command: string[]` and optional `scriptCwd`.
- Payload preview accurately reflects the submitted request body.
- Validation blocks clearly invalid input before submit.
- Tool dispatch fields and real-time logs do not regress.
- Typecheck and Debug UI build pass.
