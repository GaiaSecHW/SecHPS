CodeSwarm 排队任务不派发问题 — 确证诊断手册
============================================================
日期：2026-06-14
分支：dev
关联 commit：9db3333f（减容后 dispatched 卡死文档，仅文档未修代码）

------------------------------------------------------------
一、现象
------------------------------------------------------------
- 单 Worker，maxConcurrent=10
- 界面显示「执行中=6」（实为 DB CodeswarmWorker.currentTasks 字段，
  非真实 running 任务数；见 src/components/codeswarm/WorkerNodesTable.tsx:284-296）
- queued 状态任务不进入派发
- 把 queued 任务点「停止」→ 失败界面点「重试」后，任务能正常派发执行

------------------------------------------------------------
二、根因概述
------------------------------------------------------------
UI 的「重试」按钮调用 POST /api/codeswarm/tasks/[taskId]/dispatch，
这是一条**完全同步直发**路径：
  API → SQL 直接抢占 Worker 槽位 → HTTP POST /task → 失败事务回滚
它绕过 Redis Stream，不被 NX 锁阻塞，不读 dispatcher 内存拓扑。

而原本 queued 任务的派发走的是 **Redis Stream 链路**：
  API submitTask → XADD → dispatchLoop(XREADGROUP)
    → dispatchOne → selectWorker → sendTaskToWorker
失败时：scheduleRetry (SET NX PX) → XADD 重投

Stream 链路在多处存在「消息丢失/卡死」窗口，原 queued 任务
只有走 retry API 这条独立路径才能重新触发。

------------------------------------------------------------
三、三条卡死路径（按可能性排序）
------------------------------------------------------------

【路径 #1】dispatchOne 失败时无条件 XACK，消息从 Stream 永久消失
  位置：src/services/codeswarm-dispatcher.ts:517
  机制：dispatchOne 返回 false（无 Worker / 容量满 / 1 秒回滚节流）
        后仍然 xack。结果：Stream 消息没了，DB state 还是 queued，
        只能等 scanDbQueuedTasks 30 秒兜底；兜底又走 scheduleRetry NX 锁。

【路径 #2】scheduleRetry 的 NX 锁卡死窗口
  位置：src/services/codeswarm-dispatcher.ts:133-148
  机制：SET NX PX 5000 成功 → 进程在 XADD 之前崩溃/Redis 异常
        → 锁写了，消息没进 Stream → 5 秒锁窗口内任何
        scheduleRetry 都被静默丢弃（line 140 直接 return，无日志）
        → 等 30 秒兜底再试。

【路径 #3】dispatcher 内存 currentTasks 虚高，selectWorker 误判容量满
  位置：src/services/codeswarm-dispatcher.ts:607-632（selectWorker）
        +  onHeartbeat 内存更新 :337-338
        +  daemon.ts:425 上报公式 currentMax - semaphore.available
  机制：Worker 心跳上报值因 Semaphore 泄漏虚高，dispatcher 内存
        currentTasks 跟着虚高 → 即使 DB 还有容量，selectWorker 跳过。

------------------------------------------------------------
四、诊断决策树（按顺序执行，5 分钟内可锁定）
------------------------------------------------------------

========== Step 1：Redis Stream 现状（决定走向） ==========

# 取所有 queued 任务的 DB ID
psql -c "SELECT id FROM \"CodeswarmTask\" WHERE state='queued';" > queued_ids.txt

# Stream 里有多少消息
redis-cli XLEN codeswarm:task:queue

# Stream 里都有哪些 dbTaskId
redis-cli XRANGE codeswarm:task:queue - + COUNT 100

判决：
  Stream 里有 queued 任务对应的 dbTaskId  → 跳 Step 3
  Stream 里没有这些 dbTaskId（XLEN=0 或全是其他任务） → 走 Step 2


========== Step 2：消息丢失路径判决（#1 vs #2） ==========

# 1. NX 锁堆积情况
redis-cli KEYS "codeswarm:task:retrying:*"
for k in $(redis-cli KEYS "codeswarm:task:retrying:*"); do
  echo "$k: $(redis-cli TTL $k)s"
done

# 2. dispatcher 进程是否在跑（consumeLoop 健康）
ps -ef | grep -i codeswarm-dispatcher | grep -v grep

# 3. 最近 10 分钟的 scheduleRetry / XACK 日志
grep -E "scheduleRetry|XACK|dispatchOne|无可用 Worker" \
  logs/codeswarm-dispatcher.log | tail -100

判决矩阵：
  + retrying:* 大量堆积 + TTL>0 + 日志频繁 scheduleRetry 但没「已分发到」
    → 路径 #2 实锤（NX 锁卡死，XADD 没执行）

  + retrying:* 几乎没有 + 日志有 dispatchOne 但后续既无「已分发到」也无 scheduleRetry
    → 路径 #1 实锤（XACK 提前丢消息）

  + retrying:* 正常（0-1 个）+ 日志频繁「无可用 Worker」
    → 路径 #3 实锤（内存虚高）


========== Step 3：消息在 Stream 但不消费 ==========

# 1. pending 消息（被消费者持有但未 ACK）
redis-cli XPENDING codeswarm:task:queue dispatcher

# 2. 消费者状态（idle 时间长说明卡了）
redis-cli XINFO CONSUMERS codeswarm:task:queue dispatcher

# 3. DB 真实容量 vs dispatcher 内存判断
psql -c "
SELECT
  w.\"currentTasks\" AS db_current,
  w.\"maxConcurrent\",
  (SELECT COUNT(*) FROM \"CodeswarmTask\" t
   WHERE t.\"workerId\" = w.id
     AND t.state IN ('dispatched','running','building')) AS actual_active
FROM \"CodeswarmWorker\" w;
"

# 4. dispatcher 日志的派发失败原因
grep -E "无可用 Worker|selectWorker|currentTasks.*maxConcurrent|心跳" \
  logs/codeswarm-dispatcher.log | tail -50

判决矩阵：
  XPENDING>0 且 idle 很大 + db_current = actual_active
    → consumeLoop 卡死（dispatchLoop 死循环或异常）

  XPENDING=0 + db_current < max 但日志频繁「无可用 Worker」
    → 路径 #3 实锤（内存虚高，selectWorker 用了脏内存值）

  XPENDING=0 + XINFO 活跃 + db_current = actual_active < max
    → dispatchLoop 没把消息读出来（consumer group 异常）


========== Step 4：主动复现（最强证据） ==========

# 1. 记录一个已知 queued 任务的 ID
TASK_ID=$(psql -t -c "SELECT id FROM \"CodeswarmTask\" WHERE state='queued' LIMIT 1;")
echo "Task: $TASK_ID"

# 2. 手动注入一条 Stream 消息
redis-cli XADD codeswarm:task:queue "*" dbTaskId "$TASK_ID"

# 3. 实时观察 Stream 和 DB
watch -n 1 "redis-cli XLEN codeswarm:task:queue && \
  psql -t -c \"SELECT state FROM \\\"CodeswarmTask\\\" WHERE id='$TASK_ID';\""

# 4. 同步开 dispatcher 实时日志
tail -f logs/codeswarm-dispatcher.log | grep -E "$TASK_ID|dispatch|Worker"

判决：
  手动 XADD 后任务立即派发
    → 原本是 Stream 没消息（路径 #1 或 #2）

  手动 XADD 后任务不派发 + 日志显示「无可用 Worker」
    → 路径 #3 实锤

  手动 XADD 后任务不派发 + 日志完全没动静
    → consumeLoop 死了

五、预判与最强嫌疑
------------------------------------------------------------
基于「stop + retry 能成功」这个铁证：
  - DB 容量、Worker 链路均正常
  - 唯一能解释「原任务不派发」的是 Stream 里根本没消息了
  - Stream 没消息的最大嫌疑是 dispatchOne 失败时无条件 XACK

最强嫌疑：**路径 #1（XACK 提前丢失消息）**
位置：src/services/codeswarm-dispatcher.ts:517

实锤条件：Step 1 中 Stream XLEN=0 但 DB 有 queued 任务


------------------------------------------------------------
六、修复方向（待根因确认后实施）
------------------------------------------------------------

【方案 A：最小止血（2 处改动）】
  1. dispatchOne 失败时不 XACK，让消息留在 PEL，
     30 秒后 recoverPendingMessages 自动重投
     位置：src/services/codeswarm-dispatcher.ts:517
  2. scheduleRetry SET NX 失败时记日志 + 延长 setTimeout 重排，
     不再静默 return
     位置：src/services/codeswarm-dispatcher.ts:140

【方案 B：中等修复（解决根因）】
  3. scanDbQueuedTasks 直接调 submitTask 而非 scheduleRetry，
     绕过 NX 锁
     位置：src/services/codeswarm-dispatcher.ts:891
  4. 取消 take: 50 限制，避免大批 queued 任务排队等扫
     位置：src/services/codeswarm-dispatcher.ts:884

【方案 C：架构性修复（长期）】
  5. 统一派发入口：让 retry API 也走 dispatcher，
     或让 dispatcher 失败时也走 retry API 的同步直发路径。
     当前两条路径并存是 BUG 温床。

九、差 1 槽位场景：cancel 流程 Semaphore 泄漏（最强嫌疑）
------------------------------------------------------------

【现象】
  - 单 Worker，maxConcurrent=10
  - UI 显示「运行中=9」（界面口径未确认是 WorkerNodesTable 的
    currentTasks 还是任务列表 state='running' 计数）
  - 还有多个 queued 任务不派发
  - 关键特征：10-9=1，正好差 1 个槽位
  - 操作史：用户曾点「停止」→「失败」界面点「重试」（cancel 链路）


【根因机制（最强嫌疑）】
  codeswarm/packages/worker/src/daemon.ts:239-268 的 /task/cancel handler
  只调 cancelledTasks.add() + processMgr.terminate()，
  不调 semaphore.release()，也不删 activeTasks。

  而 Orchestrator 端 DELETE handler
  （src/app/api/codeswarm/tasks/[taskId]/route.ts:118,126-132）
  已经在 DB 端 currentTasks-1。

  结果链路：
    1. Orchestrator DB currentTasks: 10 → 9（递减）
    2. Worker 进程内 Semaphore 仍占用 1 个槽位（available=0 但 max=10）
    3. Worker 下次心跳上报 currentMax - available = 10
    4. 心跳棘轮 GREATEST(currentTasks=9, reported=10) → DB 刷回 10
    5. selectWorker 看到 currentTasks=10 >= maxConcurrent=10 → 拒绝派发
    6. 永久卡 1 个槽位


【一步实锤】

  SQL（一条即可判决）：
    SELECT
      w."nodeId",
      w."currentTasks" AS db_current,
      w."maxConcurrent",
      (SELECT COUNT(*) FROM "CodeswarmTask"
       WHERE "workerId"=w.id
         AND state IN ('dispatched','running','building')) AS actual_active,
      (SELECT COUNT(*) FROM "CodeswarmTask"
       WHERE "workerId"=w.id AND state='dispatched') AS stuck_dispatched
    FROM "CodeswarmWorker" w
    WHERE w.status='online';

  Worker 真实 Semaphore 状态：
    curl http://<worker-address>/health
    关注返回里的 available 和 maxConcurrent 字段


【判决矩阵】
  db_current | actual_active | stuck_dispatched | Worker /health available | 结论
  -----------+---------------+------------------+--------------------------+---------------------------
  10         | 9             | 0                | 0                        | 根因 1 实锤（cancel Semaphore 泄漏）
  10         | 9             | 0                | 1                        | 根因 2 实锤（心跳棘轮锁死，Worker 端正常）
  10         | 10            | 1                | 0                        | 根因 3 实锤（dispatched 卡死，phase_start 未发）
  9          | 9             | 0                | 1                        | DB 没满，走第四章 Stream 链路诊断


【三条根因详解】

  根因 1（最高概率）：cancel 流程在 Worker 端 Semaphore 泄漏
    位置：codeswarm/packages/worker/src/daemon.ts:239-268
    机制：Worker 处理 cancel 时只做 cancelledTasks.add(taskId)
          + processMgr.terminate(taskId)，不调用 semaphore.release()，
          也不删除 activeTasks。槽位要等到 executeTask 走到 success/catch 块
          （daemon.ts:740-744 或 770-774）才释放。
          但 Orchestrator 端 DELETE handler 已经在 route.ts:118
          decrementWorkerMemoryLoad + route.ts:126-132 事务里 DB currentTasks-1。
          下次心跳上报 currentMax-available=10 → 心跳棘轮把 DB 刷回 10
          → 永久卡 1 个槽位。

  根因 2：心跳棘轮 GREATEST 把瞬时虚高锁死
    位置：src/app/api/codeswarm/worker/heartbeat/route.ts:67-81
    机制：Worker 完成一个任务时存在时间窗——DB currentTasks 已 +1
          （新任务分发，codeswarm-dispatcher.ts:191）但旧任务 postResult 未到。
          Worker 心跳此时上报 currentMax-available=10。
          GREATEST(currentTasks, reported) 把 DB 锁在 10。
          注释 line 60-62 自承认有毫秒级窗口且只能等下一个 30s 心跳自动修正。
          但如果心跳上报值始终是 10（与根因 1 配合），就永远修不下来。

  根因 3：dispatched→running 转换漏事件
    位置：src/app/api/codeswarm/worker/event/route.ts:78-81
    机制：只有 phase_start 且 eventData.phase==='executing' 才把 state
          从 dispatched→running。session_created 事件 line 70-74 也能转。
          如果 Worker 在 building 阶段崩溃 / opencode run 模式
          不发 phase_start(executing)，任务永远卡 dispatched。
          此时心跳 actualActive 子查询（route.ts:74）仍把 dispatched 算进去，
          所以 currentTasks 不掉，但 UI 任务列表「运行中」过滤
          （通常 state='running'）只算 9 个。


【Worker 端 Semaphore.release() 全部路径审计】

  位置                                  | 触发条件                                  | 是否可靠
  -------------------------------------+------------------------------------------+-------------------
  daemon.ts:175                         | 重复 taskId 拒收                          | 可靠（与 tryAcquire 同步）
  daemon.ts:192                         | executeTask 异常外的兜底 finally          | 可靠
  daemon.ts:317                         | stop() 优雅关停遍历 activeTasks           | 可靠
  daemon.ts:742                         | executeTask try 块 success，postResult 后 | 可靠
  daemon.ts:772                         | executeTask catch 块，postResult 后        | 可靠
  daemon.ts:239-268 /task/cancel        | 缺失！只 terminate 不 release             | 泄漏
  process-manager.ts:589-597 error 事件 | spawn error / exitCode null               | 可能泄漏（依赖 executeTask catch 兜底）


【修复方案】

  最小修复（根因 1 实锤后）：1 处改动

    codeswarm/packages/worker/src/daemon.ts:239-268 的 /task/cancel handler 补：

      if (this.activeTasks.has(taskId)) {
        this.activeTasks.delete(taskId);
        this.semaphore.release();   // 补这一行
      }

  更稳健方案：让 executeTask 的 finally 块（daemon.ts:183-194）感知 cancel 信号，
  统一在退出路径 release，避免 cancel 路径与正常退出路径状态机分叉。


------------------------------------------------------------
十、两条 BUG 的关联
------------------------------------------------------------
  第八章场景（running=6/10）与本章场景（running=9/10）根因可能重叠：

  - 第八章的 stop+retry 能成功 = cancel 路径触发了 Semaphore 泄漏
    但 retry 走的是同步直发 API（POST /tasks/[id]/dispatch），
    用 DB 真实值判断容量，绕过了 Worker 端泄漏的 Semaphore。

  - 本章 cancel 泄漏是第八章 stop+retry 操作的副作用累积。

  - 修复建议：第八章方案 A（Stream 链路 XACK 修复）+ 本章 cancel release 补丁
    一起做，能根治两个场景。
